# Comm module sleep current: 1467 uA -> 356 uA (2026-09-08)

All currents measured with a Joulescope JS220 in the **battery lead**, USB
unplugged, board on battery. "Comm board alone" means nothing on J404.

USB-plugged is easy to mistake for a valid reading: with the cable in, the board
runs from VBUS and the battery lead shows a flat **62.9 uA**. That number, not
the presence of a COM port, is the test for whether the cable is out -- the C6's
USB-Serial/JTAG only enumerates while awake, so a sleeping board shows no port
either way.

## 1. Result

| configuration | sleep current |
|---|---|
| shipping firmware, start of day | **1467.5 uA** (also 1468, 1501 on two earlier runs) |
| after the pull-up fix, sensor rail up | **356.5 uA** |
| same, sensor rail down | **139.8 uA** |
| no GPIO holds at all | **128.3 - 128.5 uA** |

The 128.3 uA floor matches the 129.1 uA in the 2026-09-06 report's June bench
staircase to within 0.8 uA. The hardware was never the problem.

Full system (comm + ultrasonic + pressure sensor, rail up, USS metering at 1 Hz):
**floor 546.1 uA, median 649.1 uA**; the ripple is the 1 Hz captures.

## 2. What was actually wrong

### 2.1 Internal pull-ups latched into their own output drivers (1122 uA)

`gpio_reset_pin()` enables the pad's internal pull-up -- its own comment says
"for powersave reasons, the GPIO should not be floating, select pullup" -- and
`gpio_set_direction()` only touches input-enable / output-enable / open-drain.
It never clears the pull-up. So board.c's `out()` leaves every pin driving a
level WITH the pull-up still on.

A pad driven LOW then fights its own driver through the ~42k internal pull-up.
That pull-up is in the always-on domain, so an UNHELD pad powers down in deep
sleep and the conflict disappears; `gpio_hold_en()` latches it in.

MEASURED, holding pads driven LOW:

| pads held | delta |
|---|---|
| LED only | +78.4 uA |
| MODEM_PWR_EN + PWRKEY | +156.1 uA (78.1 uA each) |

A pad held HIGH costs nothing: GPIO1 high vs low measured **+12.4 uA**, which is
that pin's own load -- (3.3 - 1.9) V / R454 100k = 14 uA through D420.

FIX: `gpio_pullup_dis()` on the three pads held low, before `gpio_hold_en()`.
Three lines. Shipping firmware went **1467.5 -> 356.5 uA** with no behavioural
change: all four holds still applied, sensor rail still up, ultrasonic board
still powered between wakes.

### 2.2 The energised sensor rail (216.6 uA) -- already fixed in the schematic

Energising the switched rail costs **216.6 uA**, measured twice, under two
different pull-up configurations, with J404 empty.

It is NOT a load on the rail. It is the gate-drive divider, and the board on the
bench does not match the current schematic:

| | R419 | R420 | R421 |
|---|---|---|---|
| as built (BOM sent to JLC 2026-04-23) | 10k | 10k | 100k |
| schematic since 2026-08-18 | 1k | 1M | 1M |

With the as-built values:

    GPIO14 high -> R419 10k -> gate -> R420 10k -> GND   3.3 V / 20k   = 165 uA
    Q405 on     -> R421 100k, VSYS to drain              4.16 V / 100k =  42 uA
                                                                         -------
                                                             predicted   207 uA
                                                             measured    216.6 uA

The corrected values give 7.5 uA for the same paths, so the next build removes
~209 uA with no new work. D606 was suspected and is exonerated.

Supporting readings: with the rail ON, J404 pin 2 = 4.16 V (so nothing loads it)
and SDA/SCL = 3.3 V (so no clamp path); rail-to-GND cold = 2.9 MOhm.

### 2.3 Park mode leaked 321 uA

The two park-mode sleep paths called `bq_adc_disable()` but never
`bq_ibat_sense(false)`, leaving EN_IBAT on for exactly the long low-battery
sleeps. Fixed.

BQ25792 costs, one control bit removed per ladder rung:

| left enabled across sleep | cost |
|---|---|
| ADC in continuous conversion | **574.1 uA** |
| EN_IBAT | **321.4 uA** |
| ACDRV1, ACDRV2 | 0.0 uA each |

574.1 + 321.4 = 895.5 uA, matching an independent single-rung measurement of
895.5 uA exactly. Note the normal wake path already disabled both before sleep,
so this was never the field problem -- only park mode leaked.

## 3. Suspected and cleared

* Motion wake / `sc7a20_arm_motion()` -- disabled it, board still slept at
  1467.5 uA vs 1467.1 uA. Costs nothing. Left enabled.
* The modem and WiFi uplink -- a rung covering the entire wake path including a
  full uplink measured the same as one that skipped it.
* R405/R408 2.2k UART pull-ups -- parking IO20/IO21 before sleep changed nothing.
  The Q402/Q403 level shifters have their gates on the modem's own VDD_1V8, so
  they isolate correctly when it is unpowered.
* `esp_pm_configure()` with light sleep enabled -- +0.1 uA.
* D606 / errata 11 -- with the ultrasonic board attached and the rail down, the
  back-feed measures **+60.4 uA**, not 1.4 mA. The 1.4 mA figure belongs to
  `board_sensor_power_cycle()`, which deliberately drives SDA/SCL LOW through the
  4k7 pull-ups (2 x 3.3 V / 4k7 = 1.404 mA) for the off window only. Confirmed
  with a voltmeter: rail off, J404 pin 2 sits at 2.8 V, fed through D606's clamps
  from the 3.3 V bus. A connected ultrasonic board is therefore parasitically
  held near 2.8 V during sleep rather than being cleanly off.

## 4. Two ESP32-C6 facts worth keeping

* `gpio_deep_sleep_hold_en()` does not exist on the C6. driver/gpio.h guards it
  with `#if SOC_GPIO_SUPPORT_HOLD_IO_IN_DSLP && !SOC_GPIO_SUPPORT_HOLD_SINGLE_IO_IN_DSLP`
  and the C6 defines BOTH -- it holds pads individually, so plain
  `gpio_hold_en()` is sufficient, including on non-RTC pads like GPIO14/22/23.
  Being an RTC/LP pin (GPIO0..7) governs EXT1 wake and LP-core access, not hold.
  RTC pads are not cheaper to hold.
* `esp_sleep_pd_config(ESP_PD_DOMAIN_RTC_PERIPH, ESP_PD_OPTION_OFF)` RAISES
  deep-sleep current to 885.7 uA -- the documented light-sleep level -- and wipes
  RTC_DATA_ATTR. Do not use it.

## 5. Energy budget

Measured, comm + ultrasonic + pressure sensor, USS metering at 1 Hz:

    sleep    655 uA x 24 h                  = 15.7 mAh/day
    wakes    67.1 mC above floor x 288/day  =  5.4 mAh/day
    uplink   2.28 mAh x 1/day               =  2.3 mAh/day
                                              -------------
                                              ~23 mAh/day

against the 114 mAh/day field baseline in the 2026-09-06 report. On a 5000 mAh
cell that is ~217 days nominal; derating for usable capacity, self-discharge and
a real registered cellular session gives roughly 5 months, against ~6 weeks
before. The next board build should reach ~18 mAh/day.

## 6. NOT established

* The uplink figure is one attach ATTEMPT, not a registered session. There is no
  cellular signal at the bench, so the modem drew 351 mA for ~40 s (8.21 C =
  2.28 mAh) and failed to register. A real session may cost more; the 2026-09-06
  report modelled ~5.5 mAh/day.
* The per-wake charge comes from a SINGLE wake in one 420 s window.
* The rung-0 baseline drifted 128.5 -> 174.4 -> 139.6 uA across runs of identical
  code. Deltas within a run are consistent to ~1 uA; absolute floors across runs
  carry roughly 11-35 uA of unexplained spread.
* That the 216.6 uA is the gate divider is supported by arithmetic (207 uA
  predicted vs 216.6 uA measured) and by the BOM/schematic mismatch, but has NOT
  been confirmed by measuring the fitted resistors.

## 7. Method notes

* Peripheral state survives an ESP32 reset. The BQ25792 keeps its registers (and
  `bq_disable_watchdog()` removes the one timer that would restore defaults), and
  so does the SC7A20. A minimal "boot and sleep" image therefore proves nothing
  about persistent peripheral state -- only a ladder that TAKES STATE AWAY does.
* Encode the rung in the sleep duration (20 s + 5 s per rung). Two earlier
  ladders were mapped by plateau ORDER, and the same trace admitted two
  self-consistent mappings that gave opposite conclusions.
* Give every rung a >= 1.5 s awake window, or the USB port never enumerates and
  the board cannot be reflashed without a full power cycle.
* Always include a rung that MUST reproduce a known reference. The ladder that
  finally worked had one rung land on 128.5 uA (the known floor) and another on
  1467.1 uA (the known shipping figure). Earlier ladders had no such check and
  produced confident wrong answers.
* Audit the netlist that matches the BOARD, not the latest schematic. An hour was
  spent blaming D606 because the netlist export came from a schematic revised
  four months after the board was manufactured.

| setting | value |
|---|---|
| SAMPLE_INTERVAL_S | 300 s |
| UPLOAD_PERIOD_S | 24 h (one uplink/day) |
| USS_AUTO_PERIOD_S | 1 s (ultrasonic meters at 1 Hz) |
| MOTION_WAKE_ENABLE | 1 |

Firmware contains the pull-up-before-hold fix and the park-mode EN_IBAT fix; all
ladder instrumentation removed (main.c 1271 -> 791 lines).

Predicted ~23 mAh/day. The soak is sited where there IS cellular signal, so the
daily uplink should be a real registered session rather than the failed attach
measured at the bench -- which makes the soak the measurement that finally closes
the one term in section 6 that is still an estimate.

What to check when it comes back:

* battery discharge slope vs the predicted 23 mAh/day
* actual mAh per registered cellular session
* whether the sleep floor drifts with battery voltage (it should not, now that
  the 216.6 uA is understood as a fixed resistive divider rather than a leakage)
