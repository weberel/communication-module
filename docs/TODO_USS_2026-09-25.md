# TODO: bring the 2026-09-25 USS work onto the comm board

The ultrasonic module (USS), the uss-link library and the bench streamer changed on
2026-09-25. The comm board firmware (`idf/`) has not been touched yet, apart from the
`uss_link.h` copy. This file lists what to do, in order. Background, measurements and bench
procedure: `Calibration-data-collection/calibration/USS.md`.

## What changed on the other side (read first)

| Where | Change | Effect on the comm board |
|---|---|---|
| module firmware | capture window 110 → **140 µs after excitation** (`USS_ADC_SAMP_COUNT_SEC` 340 µs, `gap_adcsmp` 1700) | the zero offset no longer depends on composition (±4 ns from 10 to 90 % CH4, was 5–54 ns). Nothing to do, but **offsets measured before this are obsolete**. |
| module firmware | gain fallback never goes below 25 | nothing to do |
| module firmware | **abs-ToF gate**: a capture with an implausible time of flight is rejected with **code 0xE1 (`USS_CODE_TOF_HOP`)**, counted as skipped in the raw totalizer, and triggers a re-search | it is a non-122 code, so the current driver already treats it as invalid. Up to 4 are expected after every module boot. |
| module firmware | **parameter access over I2C**: registers `0x44` (id), `0x45` (i32 value), commands `USS_CMD_PARAM_SET` 0x06 / `USS_CMD_PARAM_GET` 0x07, result block `0x68..0x6F` with its own CRC | additive, PROTO stays 3. Needed for gas profiles (task 5). |
| `uss_link.h` | all of the above | **already copied** into `idf/src/uss_link.h`; all three copies are identical (MD5 `9228b793…`). Keep them in sync. |
| uss-link | `uss_param_get/set()`, and **`uss_derive.c/h`**: composition, gas properties, Re, K(Re, x), zero, low-flow cutoff, standard volumes, gas profiles | this is what the comm board should report (tasks 2–4) |

**Module settings persist in FRAM** across power cycles until the next flash. A module that
was tuned on the bench keeps those values. Read them back (`USS_CMD_PARAM_GET`) before
trusting a unit in the field.

### 2. Decide: port to uss-link, or copy only the derivation
**Decided 2026-09-25: neither. The comm board stays separate from uss-link.** It keeps its own
driver (`idf/src/uss.c`, now with `uss_param_get/set`) and its own derivation
(`idf/src/gasflow.c/h`), written for the comm board. The constants and physics must stay
numerically identical to `uss_derive.c`; `tools/gasflow_check.c` checks that on the host
(2.8 M comparisons, worst relative difference 3.5e-16). **Refit one, refit both, bump
`GF_DERIVE_VER`, rerun the check.** uss-link's ESP-IDF port was not used: it caches its own
I2C handle, which `eco_i2c_hold_low()` (the rail-cycle recovery) would delete under it.

The original options, for reference:
The comm board has its **own** `idf/src/uss.c/.h`, a separate driver from `uss-link/src/uss.c`
with a different struct (`uss_sample_t`-style vs `uss_result_t`).
- **Option A (recommended): use uss-link as the ESP-IDF component** (its `CMakeLists.txt`
  already lists `uss.c uss_derive.c uss_port_espidf.c`) and delete the local driver. One
  driver, one place to fix bugs. Cost: re-verify retry/timeout behaviour on the real bus
  (clock stretching; `USS_XFER_TIMEOUT_MS` 1000), and the STALE-seq detection in `main.c`
  must keep working.
- **Option B: copy `uss_derive.c/h` only** and write a small adapter that fills a
  `uss_result_t` from the local struct (fields used: `code, tof_ups_q40, tof_dns_q40,
  dtof_ps, amp_ups, amp_dns`). Quicker, but it leaves two drivers drifting.

### 3. Derived values per record, WITHOUT changing the record layout
The record already holds every raw input: `uss_s1`, `uss_s0`, `uss_tot_skip`,
`uss_tof_ups_q40`, `uss_tof_dns_q40`, `uss_dtof_ps`, `uss_amp_*`, `press_dmbar`, `temp_cC`.
The MS5837 sits **in the gas line** (`config.h`), which is what the derivation needs.
- [x] In `uplink.c`, when building the JSON: `gf_sample()` from the record's sample
      fields plus `press_dmbar / 10` and `temp_cC / 100`, then `gf_window()` on
      `dS1 = s1 − prev.s1`, `dS0 = s0 − prev.s0`, `dt` = time between the two records.
- [x] The predecessor is **read back from the flash ring by seq** (`flashlog_read_seq`), not kept
      in RAM, so it survives deep sleep and reboots. No predecessor → no window
      (`uss_win_err: "no_prev"`), never zero.
- [x] Window rejected (with `uss_win_err`) on SAT, `dS0 <= 0` (includes a reset and pre-PROTO 3
      records), no usable dt, no valid sample at either end, **coverage** > 1.25, or mean
      |q| > 60 SL/min. Coverage is `dS0 · tu · td / 2^40 / dt`: the time S0 claims was
      integrated, over the wall clock. It stands in for "fits the number of captures", because the
      record has no TOT_N. Field median 0.990 (eco-field-02, 2026-09-23); not judged under 60 s.
- [x] `REC_MAGIC` unchanged (ECL6). A backlog logged before this build still gets derived values.
- [x] Raw keys unchanged and still sent.
- [x] Found and fixed along the way: when a batch overflowed the JSON buffer, `drain()` still
      advanced by the full batch, so records that did not fit were marked sent without ever
      leaving the board. Buffer is now 16 KB and the advance counts only what was sent.

### 7. Things the field will do that the bench did not
- [ ] **Water vapour.** Field biogas is saturated. At 35 °C ~5.6 % H2O shifts the CH4 reading
      by ~3–4 %. At least add a "saturated at T" option, or a humidity input if a sensor exists.
- [ ] **Temperature gradients** (sun on the pipe) moved the zero by 10–25 ns on the bench
      (2026-09-24 "hotgrad"), which is ~0.15–0.35 L/min. Log the gas temperature with every
      record; flag windows where the MS5837 temperature changes fast.
- [ ] The module's hard ToF limits are **140–320 µs** (72 mm path, CH4/CO2/air). A longer
      cell or a very fast gas needs them made configurable in the module (not done yet).

### ⚠ Open question: eco-field-02 (device 4) ToF
Its telemetry for 2026-09-23/24 (`tools/eco-field-02_1d(4).csv`) shows abs ToF 132.5–133.0 µs,
all code 122, gas at 21–23 °C. On the 75 mm cell (L = 72.2 mm) that is c ≈ 548 m/s, faster
than pure CH4 (162.6 µs). `gasflow` therefore flags every sample `uss_tof_bad`, and the new
module firmware's 140 µs hard floor would reject every capture as 0xE1. Either this unit has
a different cell (path length), or its old module firmware reports ToF on a different basis.
**Resolve before flashing the new module firmware onto it.**
